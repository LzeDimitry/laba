# Security Requirements — Secure Update Client

| | |
| --- | --- |
| Назва | Безпекові вимоги — `Secure Update Client` |
| Версія | 0.1.0 |
| Статус | Draft |
| Останнє оновлення | 2026-11-06 |
| Власник | Відповідальний за безпеку |
| Пов'язані документи | `threat_model.md`, `../policy/security_policy.md` |

Вимоги сформульовано за моделлю загроз (`threat_model.md`). Кожна вимога має
ідентифікатор `SR-XX`, категорію, формулювання та посилання на загрозу або
сценарій атаки, який вона закриває.

## 1. Автентичність оновлення

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-01 | Клієнт MUST перевіряти цифровий підпис манифесту до використання будь-яких даних із нього. | A1, A3, A5 |
| SR-02 | Відкритий ключ перевірки MUST бути вбудований у клієнт (pinned) і не завантажуватися з мережі під час роботи. | A6 |
| SR-03 | Підпис MUST виконуватись алгоритмом RSA-PSS (3072+ біт, SHA-256) або Ed25519. Використання SHA-1/MD5 заборонено. | A5 |
| SR-04 | Клієнт MUST відхиляти манифест, якщо версія в ньому нижча або дорівнює поточній (захист від відкату). | A2 |
| SR-05 | Манифест MUST містити SHA-256 кожного артефакту; після завантаження хеш MUST бути перевірений повторно. | A1 |

## 2. Цілісність і застосування

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-06 | Застосування оновлення MUST виконуватись лише з staging-каталогу після повторної перевірки хешу безпосередньо перед підміною файлів. | A7 |
| SR-07 | Розпакування архіву MUST відхиляти абсолютні шляхи та `..` (path traversal). | A9 |
| SR-08 | Застосування оновлення MUST бути атомарним: при збої виконується відкат до попередньої версії. | A7 |
| SR-09 | Розмір манифесту та пакета MUST бути обмежений; перевищення ліміту є помилкою, а не попередженням. | F2, F3 |

## 3. Автентифікація та авторизація операторів

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-10 | Паролі операторів MUST зберігатись як bcrypt-хеш із cost ≥ 12; відкритий пароль не зберігається і не журналюється. | A4 |
| SR-11 | Сесія оператора MUST мати обмежений час життя та завершуватись явним виходом або після простою. | A4 |
| SR-12 | Авторизація MUST перевірятись на сервері для кожної захищеної операції; приховування елементів UI не є контролем доступу. | A4 |
| SR-13 | Публікація релізу MUST бути доступна лише ролі `release_manager`; читання метаданих — ролям `release_manager`, `auditor`, `admin`. | A4 |
| SR-14 | Підпис релізу MUST вимагати окремої автентифікації в КХС; серверний API не має доступу до приватного ключа. | A5 |

## 4. Криптографія та зберігання

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-15 | Локальний кеш пакетів MUST мати права доступу `0700` для каталогу та `0600` для файлів. | D1 |
| SR-16 | Чутливі метадані (журнали, резервні копії) MUST зберігатись у зашифрованому вигляді (AES-GCM). | D2, D4 |
| SR-17 | Ключі та секрети MUST зберігатись поза репозиторієм; їх поява в коміті блокує реліз. | A10 |
| SR-18 | Уся передача даних між клієнтом і сервером MUST виконуватись через TLS 1.2+; HTTP заборонено. | F1, F2, F3 |

## 5. Процес розробки та збірки

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-19 | Збірка релізу MUST виконуватись із фіксованого коміту; артефакт MUST мати provenance-запис. | A8 |
| SR-20 | Нові залежності MUST перевірятись на відомі вразливості (`pip-audit`) і фіксуватись за версією. | A8 |
| SR-21 | CI MUST NOT мати доступу до приватного ключа підпису; підпис виконується окремим кроком. | A5, A10 |
| SR-22 | Логи збірки MUST не містити значень секретів; вивід змінних із секретами маскується. | A10 |

## 6. Журналювання та підзвітність

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-23 | Кожна публікація релізу MUST фіксуватись у журналі аудиту: суб'єкт, час, версія, канал, результат. | E2, P2 |
| SR-24 | Клієнт MUST вести локальний журнал установок: версія, час, результат перевірки підпису. | E1, P1 |
| SR-25 | Записи аудиту MUST бути доступні лише читанням для ролі `auditor`; зміна записів заборонена. | D4 |

## 7. Стійкість та обробка помилок

| ID | Вимога | Покриває |
| --- | --- | --- |
| SR-26 | Будь-яка помилка перевірки підпису, хешу або версії MUST призводити до відмови від установки (fail securely). | A1, A2 |
| SR-27 | Повідомлення про помилку MUST NOT розкривати внутрішні шляхи, версії бібліотек і деталі криптографії. | P1, P2 |
| SR-28 | Повторні спроби завантаження MUST бути обмежені (експоненційна затримка, максимум 3 спроби). | D, F3 |
