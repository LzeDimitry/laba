## 1. Scope

Модель охоплює:

- настільний клієнт `suc-client` (перевірка версій, завантаження, верифікація,
  застосування оновлення);
- серверний API `suc-server` (канали оновлень, метадані релізів, облікові
  записи операторів);
- офлайн-утиліту підпису `suc-signer` та сховище ключів;
- процес збірки релізу (CI);
- взаємодію з зовнішнім сховищем артефактів (CDN).

Поза межами моделі: безпека операційної системи та її антивірусного захисту,
фізичний доступ до обладнання, внутрішня реалізація CDN-провайдера, безпека
компрометації браузера користувача.

## 2. System Overview

Система складається з клієнта, який періодично звертається до серверного API за
манифестом оновлення, завантажує пакет із CDN, перевіряє підпис і контрольну
суму та застосовує оновлення з можливістю відкату. Релізи готуються CI та
підписуються окремою офлайн-утилітою з ключем у КХС.

Типи елементів DFD:

- **External Interactor** — зовнішній користувач або система;
- **Process** — компонент, що виконує обробку;
- **Data Store** — сховище даних;
- **Data Flow** — передавання даних між елементами;
- **Trust Boundary** — межа між областями з різним рівнем довіри.

### 2.1. Елементи системи

| ID | DFD Type | Name |
| --- | --- | --- |
| E1 | External Interactor | Користувач робочої станції |
| E2 | External Interactor | Оператор релізу |
| E3 | External Interactor | CDN / сховище артефактів |
| P1 | Process | `suc-client` |
| P2 | Process | `suc-server` API |
| P3 | Process | `suc-signer` (офлайн-підпис) |
| P4 | Process | Build pipeline (CI) |
| D1 | Data Store | Локальний кеш і staging-каталог |
| D2 | Data Store | База метаданих релізів |
| D3 | Data Store | Сховище ключів підпису (КХС) |
| D4 | Data Store | Журнал аудиту |
| F1 | Data Flow | Client -> Server (перевірка версії) |
| F2 | Data Flow | Server -> Client (підписаний манифест) |
| F3 | Data Flow | CDN -> Client (пакет оновлення) |
| F4 | Data Flow | Client -> Local cache (перевірений пакет) |
| F5 | Data Flow | Build -> Signer (хеш артефакту) |
| F6 | Data Flow | Signer -> Server (підпис і манифест) |
| F7 | Data Flow | Client -> Server (журнал/телеметрія) |
| TB1 | Trust Boundary | Клієнт / Мережа |
| TB2 | Trust Boundary | Сервер / Інфраструктура підпису |

### 2.2. Зв'язки

- `E1` взаємодіє з `P1` (запуск перевірки оновлення, підтвердження установки).
- `E2` взаємодіє з `P2` (керування каналами) та з `P3` (ініціювання підпису).
- `P1` передає запит до `P2` через `F1`, перетинаючи `TB1`.
- `P2` повертає манифест через `F2`, перетинаючи `TB1`.
- `P1` завантажує пакет з `E3` через `F3`, перетинаючи `TB1`.
- `P1` зберігає перевірений пакет у `D1` через `F4`.
- `P4` передає хеш артефакту до `P3` через `F5`, перетинаючи `TB2`.
- `P3` передає підписаний манифест до `P2` через `F6`, перетинаючи `TB2`.
- `P3` використовує `D3` для операцій підпису.
- `P1` передає журнал до `P2` через `F7`.
- `P2` пише події до `D2` та `D4`.

## 3. STRIDE Analysis

Канонічна відповідність STRIDE типам елементів DFD:

| DFD Element | S | T | R | I | D | E |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |
| External Interactor | ✓ |  | ✓ |  |  |  |
| Data Flow |  | ✓ |  | ✓ | ✓ |  |
| Data Store |  | ✓ |  | ✓ | ✓ |  |
| Process | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

Позначення: **S** — Spoofing; **T** — Tampering; **R** — Repudiation;
**I** — Information Disclosure; **D** — Denial of Service;
**E** — Elevation of Privilege.

### 3.1. Загрози за елементами

| Element | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| **E1 Користувач** *(External Interactor)* | Зловмисник може видати себе за користувача, якщо отримає доступ до його сесії або локальної конфігурації. | - | Користувач може заперечувати ініціювання встановлення оновлення за відсутності локального журналу дій. | - | - | - |
| **E2 Оператор релізу** *(External Interactor)* | Викрадені облікові дані оператора дозволяють публікувати довільні релізи. | - | Оператор може заперечувати публікацію релізу, якщо дія не пов'язана з його обліковим записом в аудиті. | - | - | - |
| **E3 CDN** *(External Interactor)* | Підміна CDN-вузла (DNS/маршрутизація) дозволяє віддавати сторонній вміст. | - | - | CDN бачить, які пакети та коли завантажує клієнт. | Блокування CDN робить доставку оновлень неможливою. | - |
| **P1 `suc-client`** *(Process)* | Підміна бінарника клієнта дозволяє діяти від його імені. | Локальна модифікація trust store або конфігурації знімає перевірку підпису. | Дії клієнта не фіксуються локально, тому факт установки складно довести. | Кеш пакетів може містити дані, доступні іншим локальним користувачам. | Нескінченний цикл перевірки або повторне завантаження великого пакета виснажує канал. | Помилка в логіці staging дозволяє записати файл поза цільовим каталогом. |
| **P2 `suc-server` API** *(Process)* | Запит може виконуватись від імені іншого оператора через підроблений токен. | Вхідні параметри каналу або версії можуть бути змінені для підміни манифесту. | Відсутність повного аудиту не дозволяє пов'язати публікацію з суб'єктом. | API може повернути манифест каналу, до якого оператор не має доступу. | Потік запитів може виснажити ресурси сервера. | Дефект перевірки ролі дозволяє читачу публікувати релізи. |
| **P3 `suc-signer`** *(Process)* | Підпис може бути виконаний від імені іншого оператора, якщо КХС не вимагає автентифікації. | Підписання модифікованого артефакту без перевірки хешу. | Неможливо довести, хто саме ініціював підпис. | Приватний ключ може бути витягнутий з пам'яті процесу. | Недоступність підпису блокує випуск релізів. | Компрометація ключа дає можливість підписувати будь-які пакети. |
| **P4 Build pipeline** *(Process)* | Підміна кроку збірки дозволяє зібрати артефакт із чужого коду. | Залежність або скрипт збірки може бути підмінена (supply chain). | Відсутність provenance-запису ускладнює доведення походження артефакту. | Секрети CI можуть потрапити у логи збірки. | Збій CI блокує випуск. | Виконання довільного коду через небезпечний крок збірки. |
| **D1 Локальний кеш** *(Data Store)* | - | Пакет у кеші може бути підмінений іншим локальним процесом до застосування. | - | Вміст кешу доступний іншим користувачам системи. | Заповнення диска блокує оновлення. | - |
| **D2 Метадані релізів** *(Data Store)* | - | Записи можуть бути змінені або видалені напряму в БД. | - | Розкриття ще не опублікованих релізів. | Пошкодження БД блокує видачу манифестів. | - |
| **D3 Сховище ключів** *(Data Store)* | - | Підміна ключа перевірки в trust store клієнта. | - | Витік приватного ключа підпису. | Недоступність КХС блокує підпис. | Компрометація ключа = повна підміна оновлень. |
| **D4 Журнал аудиту** *(Data Store)* | - | Записи аудиту можуть бути змінені або видалені. | - | Журнал містить дані про користувачів та релізи. | Заповнення журналу блокує роботу. | - |
| **F1 Client -> Server** *(Data Flow)* | - | Параметри запиту можуть бути змінені для отримання манифесту іншого каналу. | - | Перехоплення розкриває версію та канал клієнта. | Потік може бути заблокований або перевантажений. | - |
| **F2 Server -> Client** *(Data Flow)* | - | Манифест може бути підмінений у транспорті. | - | Манифест розкриває перелік майбутніх релізів. | Підміна на великий манифест виснажує пам'ять клієнта. | - |
| **F3 CDN -> Client** *(Data Flow)* | - | Пакет може бути підмінений під час завантаження. | - | Вміст пакета може бути перехоплений. | Підміна на великий файл виснажує канал і диск. | - |
| **F4 Client -> Local cache** *(Data Flow)* | - | Файл може бути змінений між перевіркою та застосуванням (TOCTOU). | - | - | - | - |
| **F5 Build -> Signer** *(Data Flow)* | - | Хеш артефакту може бути підмінений до підпису. | - | - | - | - |
| **F6 Signer -> Server** *(Data Flow)* | - | Підписаний манифест може бути підмінений на інший валідний. | - | - | - | - |
| **F7 Client -> Server** *(Data Flow)* | - | Дані телеметрії можуть бути сфальсифіковані. | - | Телеметрія розкриває відомості про стан робочої станції. | Потік телеметрії може бути використаний для флуду. | - |
| **TB1 Клієнт / Мережа** *(Trust Boundary)* | - | - | - | Усі дані з мережі є недовіреними до перевірки підпису. | - | - |
| **TB2 Сервер / Підпис** *(Trust Boundary)* | - | - | - | Приватний ключ не повинен перетинати межу в бік сервера. | - | - |

## 4. Ключові сценарії атак

| ID | Сценарій | Уражений елемент | STRIDE | Наслідок |
| --- | --- | --- | --- | --- |
| A1 | Підміна пакета на CDN або в транспорті | F3 | T | Встановлення шкідливого оновлення |
| A2 | Відкат на вразливу версію (rollback attack) | F2, P1 | T | Повернення відомої вразливості |
| A3 | Підміна манифесту з іншого каналу | F1, F2 | T, E | Отримання нерелізної збірки |
| A4 | Викрадення облікових даних оператора | E2, P2 | S, E | Публікація довільного релізу |
| A5 | Компрометація приватного ключа підпису | D3, P3 | S, T, E | Підпис будь-якого пакета |
| A6 | Підміна trust store у клієнта | P1, D3 | T, E | Вимкнення перевірки підпису |
| A7 | TOCTOU між перевіркою та застосуванням | D1, F4 | T | Застосування неперевіреного файлу |
| A8 | Supply chain атака через залежність | P4 | T, E | Код зловмисника в релізі |
| A9 | Path traversal при розпакуванні архіву | P1 | E | Запис файлів поза цільовим каталогом |
| A10 | Витік секретів CI у логи | P4 | I | Компрометація інфраструктури |

## 5. Залишкові ризики

| Ризик | Причина | Прийнятність |
| --- | --- | --- |
| Компрометація кінцевої станції з правами адміністратора | Поза межами системи | Прийнятний, компенсується підписом пакетів |
| Повна компрометація КХС разом із приватним ключем | Фізична/організаційна площина | Не прийнятний, потребує процедури ротації |
| Відмова CDN | Зовнішній сервіс | Прийнятний, передбачено повторні спроби |
