## 1. Що захищається

| Дані | Чутливість | Механізм |
| --- | --- | --- |
| Манифест оновлення | висока (керує встановленням) | підпис RSA-PSS + SHA-256 |
| Пакет оновлення | висока | SHA-256 у манифесті, підпис манифесту |
| Локальний кеш пакетів | середня | права доступу 0700/0600, AES-GCM для метаданих |
| Журнали аудиту | середня | AES-GCM перед записом у сховище |
| Резервні копії метаданих | висока | AES-GCM |
| Облікові дані операторів | критична | bcrypt (необоротне хешування) |
| Приватний ключ підпису | критична | зберігається лише в КХС |

## 2. Вибір алгоритмів

| Задача | Алгоритм | Обґрунтування |
| --- | --- | --- |
| Конфіденційність даних | AES-256-GCM | автентифіковане шифрування, стандарт для нових систем |
| Потокове шифрування (навчальне) | AES-256-CTR | показує відсутність автентичності |
| Цілісність артефактів | SHA-256 | стійкість до колізій, швидкість |
| Автентичність повідомлень | HMAC-SHA256 | симетричний контроль цілісності |
| Паролі | bcrypt, cost ≥ 12 | навмисна повільність |
| Підпис релізів | RSA-PSS 3072 / Ed25519 | асиметрична автентичність |

Власна реалізація криптографічних алгоритмів заборонена; використовується
бібліотека `cryptography`.

## 3. Де і коли виконується шифрування

1. **Під час формування релізу** — сервер не шифрує сам пакет: автентичність
   забезпечується підписом манифесту, а конфіденційність не потрібна, бо
   пакет призначений для публічної доставки.
2. **Під час зберігання метаданих** — журнали та резервні копії шифруються
   AES-GCM ключем, що зберігається окремо від бази.
3. **Під час роботи клієнта** — локальні метадані кешу шифруються ключем
   користувача; сам пакет не шифрується повторно.

## 4. Керування ключами

| Ключ | Де зберігається | Ротація |
| --- | --- | --- |
| Ключ підпису релізів | КХС (PKCS#11) | раз на рік або при компрометації, з перехресним підписом |
| Ключ журналів | файл поза репозиторієм, права 0600 | раз на рік |
| Ключ резервних копій | окреме сховище секретів | раз на рік |
| Ключ клієнта | локальне сховище користувача | при перевстановленні |

Правила: ключ ніколи не потрапляє в репозиторій, логи або артефакти збірки;
кожен ключ має власника та строк дії; після ротації старі дані
перешифровуються або позначаються як застарілі.

## 5. Чому не CTR для робочих даних

У режимі CTR шифротекст є XOR відкритого тексту з гамою. Одна відома пара
«відкритий текст — шифротекст» розкриває гаму, після чого зловмисник формує
валідний шифротекст для будь-якого власного тексту без знання ключа.
Експеримент `experiments/lab6/ctr_attack.py` демонструє підміну номера
варіанта на 99 саме цим способом.

Тому для всіх робочих даних використовується AES-GCM: тег автентифікації
робить підміну байта шифротексту або заголовка (AAD) таким, що виявляється
під час розшифрування.

## 6. Перевірка

Модульні тести (`tests/test_crypto.py`) перевіряють:

- оборотність CTR та повторне використання гами;
- унікальність IV та валідацію довжини;
- оборотність AES-GCM разом з AAD;
- виявлення підміни байта шифротексту (`InvalidTag`);
- виявлення зміни AAD;
- унікальність nonce для GCM.
