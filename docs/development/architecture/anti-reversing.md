## 1. Що захищається в клієнті

| Компонент | Чому цікавий зловмиснику | Метод |
| --- | --- | --- |
| Перевірка ліцензії | обхід обмежень | приховування констант, непрозорі предикати |
| Перелік доступних функцій | розширення прав | контроль цілісності, серверна перевірка |
| Вбудований відкритий ключ | підміна trust store | перевірка цілісності бінарника |
| Логіка вибору каналу | отримання нерелізних збірників | ускладнення потоку керування |
| Рядки повідомлень | пошук точок відмови | динамічна побудова рядків |

## 2. Обрані методи

| Метод | Що дає | Обмеження |
| --- | --- | --- |
| Хешування констант | у коді немає контрольного рядка | хеш усе одно можна знайти і замінити |
| Приховування констант через XOR/hex | ускладнює пошук рядків | обчислюється під час виконання |
| Перетворення потоку керування (flattening) | лінійний код стає циклом зі `match` | читається, але довше |
| Непрозорі предикати | умови виглядають залежними від даних | компілятор їх не прибирає, людина помічає |
| Непрямі виклики (`getattr`, `chr`) | приховує справжні назви функцій | потребує пояснення у звіті |
| Розбиття рядків | ускладнює `strings` | збирається під час виконання |

## 3. Що не використовується і чому

- **Пакування (packer)** — ускладнює підтримку та антивірусну репутацію, не
  дає принципового захисту.
- **Самомодифікація коду** — крихка, ламає підпис артефакту.
- **Анти-налагоджувальні перевірки** — дратують користувачів і легко
  обходяться.

Принцип: обфускація **ускладнює** аналіз, але не є межею безпеки. Справжній
захист забезпечують криптографія та серверні перевірки.

## 5. Що ускладнилося для аналітика

1. Пошук контрольної константи через `strings` і простий `grep` не дає
   результату.
2. Основна логіка рознесена по шести функціях із беззмістовними іменами.
3. Потік керування розбито на стани, тому доводиться відновлювати порядок
   виконання вручну.
4. Непрозорий предикат виглядає залежним від даних, хоча завжди істинний.
5. Виклики `print` приховані за динамічно побудованим ім'ям.

Що **не** ускладнилося: динамічний аналіз під налагоджувальником усе ще
показує значення змінних, а отже повний захист без серверної перевірки
недосяжний.

## 6. Висновки для проєкту

- Обфускація застосовується лише до клієнтських перевірок, які дублюються на
  сервері.
- Критичні рішення (публікація релізу, підпис) ніколи не ухвалюються лише в
  клієнті.
- Після обфускації обов'язково виконується повторний аналіз і регресійні
  тести: поведінка мусить збігатися з прозорою версією.
