## 1. Модель розповсюдження

Обрано **Subscription (підписка) з елементами Perpetual для серверної частини**.

| Компонент | Модель | Умови |
| --- | --- | --- |
| `suc-client` | Subscription | строк дії ліцензії, набір функцій |
| `suc-server` | Perpetual | безстрокова ліцензія, ліміт операторів |
| `suc-signer` | входить до серверної ліцензії | окремо не продається |

Обґрунтування: клієнт оновлюється постійно, тому підписка природно відповідає
моделі постачання; сервер розгортається на інфраструктурі замовника і
вимагає безстрокової ліцензії.

## 2. Ліцензійні умови

Ліцензія — підписаний JSON-документ із полями:

| Поле | Призначення |
| --- | --- |
| `product_id` | ідентифікатор продукту |
| `license_owner` | власник ліцензії |
| `expires_at` | строк дії (ISO 8601) |
| `features` | перелік доступних функцій |
| `license_id` | унікальний ідентифікатор ліцензії |

Додатково перевіряються: строк дії не вичерпано, продукт відповідає,
запитана функція входить до переліку.

## 3. Механізм контролю

| Перевірка | Де виконується | Чому |
| --- | --- | --- |
| Перевірка підпису ліцензії | локально в клієнті | не потребує мережі, працює офлайн |
| Перевірка строку дії | локально + сервер | локально — для офлайну, на сервері — авторитетно |
| Перевірка переліку функцій | локально перед операцією | відсікає виклик недоступної функції |
| Виявлення повторного використання `license_id` | на сервері | захист від копіювання ліцензії |
| Перевірка цілісності пакетів оновлення | локально | захист від підміни коду |

Приватний ключ зберігається лише в КХС розробника і ніколи не передається
клієнту. Відкритий ключ вбудований у клієнт.

## 4. Чому підпис, а не MAC і не хеш

| Варіант | Проблема |
| --- | --- |
| MDC (звичайний хеш) | зловмисник змінює ліцензію і перераховує хеш |
| MAC (HMAC) | ключ перевірки мусить бути в клієнта, отже його можна витягнути і підробити ліцензію |
| Цифровий підпис | клієнт має лише відкритий ключ; підробити підпис без приватного ключа неможливо |

## 5. Захист від копіювання

- Ліцензія прив'язується до `license_id`, який сервер фіксує під час активації.
- Повторна активація того самого `license_id` з іншого пристрою блокується
  або вимагає підтвердження.
- Клієнт не зберігає приватний ключ, тому не може видати нову ліцензію.
- Критичні перевірки дублюються на сервері: локальний обхід не дає доступу до
  серверних операцій.

## 6. Компоненти, що потребують перевірки автентичності

| Компонент | Механізм |
| --- | --- |
| Файл ліцензії | RSA-PSS + SHA-256 |
| Манифест оновлення | RSA-PSS + SHA-256 |
| Пакет оновлення | SHA-256 у манифесті |
| Оновлення самого клієнта | підпис того самого релізу |

## 7. Результати експерименту

- RSA 3072, підпис RSA-PSS із SHA-256: розмір підпису 384 байти.
- Перевірка оригінальної ліцензії — `Verified OK`.
- Після зміни `expires_at` без оновлення підпису — `Verification failure`
  (`bad signature`).

## 8. Простежуваність

| Вимога | Реалізація |
| --- | --- |
| SR-01, SR-03 | підпис RSA-PSS 3072 / SHA-256 |
| SR-02 | відкритий ключ вбудований у клієнт |
| SR-14 | приватний ключ лише в КХС |
| SR-19 | підпис релізу окремим кроком |
