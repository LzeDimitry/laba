Документ фіксує рішення, ухвалені під час лабораторної роботи №4, і є
джерелом вимог для реалізації в `src/suc/auth/`.

## 1. Ідентифікація

| Суб'єкт | Ідентифікатор | Незмінність | Примітка |
| --- | --- | --- | --- |
| Оператор релізу | `user_id` (16 hex) | незмінний | внутрішній ключ, не показується користувачу |
| Оператор релізу | `email` | змінюваний | публічний логін, нормалізується до нижнього регістру |
| Клієнт оновлення | `client_id` (UUID v4) | незмінний | генерується локально, не є секретом |

Внутрішній `user_id` відокремлений від публічного `email`, щоб зміна пошти не
розривала зв'язки із записами аудиту та журналами релізів.

Правила ідентифікації:

1. Вхід виконується лише за `email`, регістр не має значення.
2. `client_id` не використовується для автентифікації — лише для кореляції
   журналів оновлень.
3. Відсутній користувач і невірний пароль дають однакову відповідь (захист від
   переліку акаунтів).

## 2. Методи автентифікації

| Метод | Обов'язковість | Сценарій |
| --- | --- | --- |
| Пароль | обов'язковий | первинний вхід оператора |
| TOTP (RFC 6238) | обов'язковий для ролі `admin`, опційний для інших | другий фактор після пароля |
| Ключ підпису в КХС | обов'язковий | підпис релізу, окрема автентифікація в КХС |

Багатофакторна автентифікація реалізована як «пароль + TOTP». Коди TOTP
перевіряються з вікном ±30 секунд для компенсації розбіжності годинників.

## 3. Зберігання автентифікаційних даних

- Пароль зберігається лише як bcrypt-хеш із параметром вартості 12.
- Відкритий пароль не зберігається, не журналюється і не передається у
  відкритому вигляді.
- bcrypt враховує лише перші 72 байти входу; модуль `passwords.py` фіксує це
  явно, щоб поведінка не залежала від версії бібліотеки.
- Секрет TOTP зберігається окремим полем користувача і ніколи не потрапляє в
  журнали.
- Приватний ключ підпису не зберігається в системі взагалі — він знаходиться
  в КХС.

## 4. Перевірка під час входу

1. Нормалізація `email`, пошук користувача.
2. Перевірка, що акаунт не вимкнений і не заблокований.
3. Перевірка пароля через `bcrypt.checkpw`.
4. Невдача → `failed_attempts += 1`; після 5 невдач акаунт блокується.
5. Успіх → лічильник скидається, створюється сесія.
6. Якщо в користувача налаштований TOTP — сесія створюється з
   `mfa_passed=False` і не дає доступу до захищених операцій до підтвердження
   коду.

## 5. Стан автентифікованого користувача

| Властивість | Значення |
| --- | --- |
| Токен сесії | `secrets.token_urlsafe(32)`, 256 біт ентропії |
| Зберігання токена | у сховищі лише SHA-256 від токена |
| Ідлінг-таймаут | 15 хвилин |
| Абсолютний таймаут | 8 годин |
| Ротація | після зміни пароля та після успішного MFA |
| Порівняння | `secrets.compare_digest` (сталий час) |

## 6. Завершення сеансу

- Явний вихід → `revoke(token)`.
- Зміна пароля або блокування акаунта → `revoke_all(user_id)`.
- Перевищення таймауту → сесія видаляється під час наступного звернення.
- Завершення сеансу не залежить від клієнта: рішення ухвалює сервер.

## 7. Простежуваність до вимог

| Вимога | Реалізація |
| --- | --- |
| SR-10 (bcrypt cost ≥ 12) | `passwords.hash_password`, `MIN_COST` |
| SR-11 (час життя сесії) | `sessions.SessionStore`, `IDLE_TIMEOUT`, `ABSOLUTE_TIMEOUT` |
| SR-12 (перевірка на сервері) | `UserStore.authenticate`, `SessionStore.get` |
| SR-13 (ролі) | поле `User.role`, перевіряється в модулі авторизації |

## 8. Результати експериментів (ЛР4)

- bcrypt із cost=12: близько 190 мс на одну перевірку.
- SHA-256: близько 2 мс на повний прохід словника з 20 кандидатів.
- Перебір 20 кандидатів: SHA-256 — 0.04 с, bcrypt — 3.9 с (у ~100 разів довше).
- Доповнення базового рядка понад 72 байти не змінює результат перевірки.
